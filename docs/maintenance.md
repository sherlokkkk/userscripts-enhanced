# 维护路线

本仓库是 quoid/userscripts 的非官方分支。许可证保持 GPL-3.0，修改与分发须遵守 LICENSE。

## 发布前阻塞

1. 替换继承的特权 realm 内动态执行模式。用户脚本必须无法访问 browser、扩展存储或其他脚本；遮蔽全局变量不构成安全隔离。先让 `npm run audit:sandbox` 的真实攻击复现失败，再将门禁改为通过；不能删除或跳过门禁。
2. 在 Safari 真机完成隔离攻击、工具栏菜单、frame 导航、双窗口、后台重启、权限和生命周期测试。Node 模型测试不等价于此步骤。
3. 完成原生导入/备份/更新恢复故障注入，特别是文件与 browser.storage 跨存储失败、并发编辑及恢复中断。

## 每次变更

运行 JS/CSS lint、相关测试及安全门禁；原生变更运行 `scripts/test-native.sh`。修改构建、权限或签名后重建 Debug/Release 并验证产物。Safari 交互变更必须补真机记录，注明浏览器版本、脚本版本和实际结果。安全门禁当前失败时不可发行可日用版本。

上游合并先记录 commit，保留 Enhanced 的身份、授权与路由测试；不要直接复制上游旧的任意 XHR、存储或标签代理回当前桥。同步审查 MV2 非持久背景事件注册、Safari API 支持和 CodeMirror/Svelte 依赖变化。

## 后续功能

优先：强隔离和权限审计 → Safari 完整菜单验收 → 备份事务恢复 → 细粒度脚本/网站授权 → 真实脚本兼容性。再实现通知、下载、批量值 API、URL 变化事件、收藏、运行/错误统计、可选数据删除、编辑器诊断和格式化。Cookie/webRequest 与 unsafeWindow 需先核查平台与安全模型，不能用放宽权限代替实现。

性能门槛应由真实 Safari 的 IPC、CPU、内存、SPA 导航和长时间运行建立。现有 Node 微基准只用来发现注册表算法回退，不作为日常使用性能结论。
